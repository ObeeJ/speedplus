# SpeedPlus Go-Live Checklist

Generated from a read-only production-readiness review (branch `dev`, commit `b43056f`) of `docker-compose.yml`, `apps/api/Dockerfile`, `apps/osrm/Dockerfile`, `.github/workflows/api-ci.yml`, `docs/OPS-RUNBOOK.md` (including Sections G/H — DB backup/restore and incident response), and `apps/api/.env.example`. No application code was changed.

## (a) Already satisfied / verified

- [x] **No hardcoded production secrets.** `docker-compose.yml` (lines ~66-77) hardcodes `JWT_SECRET`, `PAYCODE_SECRET`, `QUOTE_SECRET`, `ENCRYPTION_KEY` — all explicitly labeled dev-only ("Generated with: openssl rand -hex 32", "intentionally committed for local dev convenience. Production secrets must come from Railway / environment secrets"). All payment-gateway/PII keys (`PAYSTACK_SECRET_KEY`, `FLUTTERWAVE_SECRET_KEY`, `MONNIFY_*`, `PREMBLY_API_KEY`, `R2_*`, `SENDBYTE_API_KEY`) are left blank in compose. `apps/api/.env.example` documents every required var with placeholders, not real values.
- [x] `.github/workflows/api-ci.yml` has a `gitleaks` job (secret scanning, full git history via `fetch-depth: 0`) and a `govulncheck` job (dependency/stdlib vuln scan, intentionally non-blocking for stdlib-only advisories per the comment at lines 109-112).
- [x] CI gates the Go backend: `build-test` job runs `go vet ./...`, `go build ./...`, and `go test -race -coverprofile=... ./...` (lines 84-91) against real Postgres/PostGIS + Redis service containers before merge.
- [x] CI gates the frontend too: `typecheck` job runs `tsc --noEmit` for `@speedplus/types`, `@speedplus/api-client`, and all four Next.js apps (customer/admin/driver/merchant); `lint` job runs `pnpm turbo lint` with `--max-warnings=0` per app; `e2e` job runs a full Playwright order-flow suite after `build-test` passes; `typecheck` job also runs `pnpm audit --audit-level=high`.
- [x] `sonarqube` job uploads Go coverage and runs static analysis on every push, gated on `build-test` passing first.
- [x] API exposes health endpoints: `apps/api/cmd/server/main.go:283-284` registers `GET /healthz` and `GET /readyz`.
- [x] `docker-compose.yml` wires a `healthcheck:` block for `postgres`, `redis`, and `api` services with sensible intervals/retries.
- [x] `docs/OPS-RUNBOOK.md` Section F explicitly documents the OSRM SPOF risk, the haversine fallback behavior, and the production requirement of 2+ instances behind a load balancer — the gap is *known and documented*, not silently missing.
- [x] `docs/OPS-RUNBOOK.md` Section G documents Postgres backup cadence (daily snapshot + WAL/PITR), manual `pg_dump`/`pg_restore` procedure, and a mandatory dual-admin sign-off + escrow-reconciliation check before cutover — solid money-safety process for the restore path.
- [x] `docs/OPS-RUNBOOK.md` Section H defines SEV1/SEV2/SEV3 severity levels, a documented rollback procedure (redeploy previous known-good image, backward-compatible migration convention, independent frontend rollback), and a "freeze escrow before root-causing" rule for payment-webhook incidents.
- [x] `apps/api/Dockerfile` uses a distroless nonroot final image (`gcr.io/distroless/static-debian12:nonroot`) with `USER nonroot:nonroot` — good attack-surface hygiene, multi-stage build keeps the Go toolchain out of the runtime image.

## (b) Must-fix before launch

- [ ] **OSRM has no production deployment path with redundancy — the documented requirement in OPS-RUNBOOK Section F is not reflected anywhere in config.** `docker-compose.yml`'s `osrm` service (lines ~34-41) is an explicit placeholder (`entrypoint: sh -c "echo 'OSRM placeholder...' && sleep infinity"`) that does nothing. The real image, `apps/osrm/Dockerfile` + `apps/osrm/start.sh`, is never referenced by `docker-compose.yml`, any workflow, or any Railway/deploy config file (none exists in the repo). There is exactly one Dockerfile defining one instance — no load-balancer definition, no second-instance service, nothing enforcing the "at least two instances" requirement Section F itself states. Confirm this is provisioned manually in Railway before launch, and if so, capture that config (service count, LB) in the repo or in OPS-RUNBOOK so it isn't tribal knowledge.
- [ ] **API `docker-compose.yml` healthcheck (`wget -qO- http://localhost:8000/healthz`, line ~130) will not run against `apps/api/Dockerfile`'s actual final image.** The final stage is `gcr.io/distroless/static-debian12:nonroot`, which ships no shell and no `wget` binary. If production orchestration (Railway) invokes this same healthcheck definition — or if anyone assumes `docker compose up` against the real Dockerfile exercises the healthcheck — it will error out (`exec: "wget": not found` / no shell to run `CMD-SHELL`), not just fail. Verify how Railway is actually configured to health-check the API (HTTP probe at the platform level bypasses this, but the compose file itself is broken evidence for anyone testing locally). Fix: either add a tiny statically-linked healthcheck binary to the distroless image, or drop the compose `healthcheck:` block in favor of the orchestrator's own HTTP probe against `/healthz`.
- [ ] **No `HEALTHCHECK` instruction in either `apps/api/Dockerfile` or `apps/osrm/Dockerfile`.** Both rely entirely on `docker-compose.yml`'s external healthcheck definitions (and OSRM's is a no-op `test: ["CMD", "true"]` placeholder, not a real check even in dev). If prod deploys these images directly through a platform that doesn't reuse this compose file's healthcheck stanza, there is no liveness signal at the image level. Confirm Railway service settings actually point a health probe at `/healthz` and `/readyz` for the API, and at OSRM's `/route` or equivalent for the routing service — no Railway config file exists in this repo to verify against, so this can't be confirmed from code alone.
- [ ] **`PAYSTACK_WEBHOOK_HASH` / `FLUTTERWAVE_HASH` are undocumented beyond a blank placeholder in `.env.example` and `docker-compose.yml`.** No comment explains where to source them or what the API does if they're unset in `ENVIRONMENT=production` (fail closed vs. silently accept unverified webhooks). Given this gates real money movement, confirm and document the fail-closed behavior before launch.
- [ ] **No documented production value for `TRUSTED_PROXIES`**, only an illustrative example ("Railway: 100.64.0.0/10") in both `docker-compose.yml` and `.env.example`. This affects `ClientIP()` correctness for rate-limiting/fraud logic — confirm and pin the real value for whatever network Railway (or the actual prod host) puts the API behind.
- [ ] **No CD/deploy workflow exists in `.github/workflows/`** — `api-ci.yml` only builds/tests/scans, there is no docker build+push or Railway-deploy-trigger job. If deployment is handled by Railway's own git-integration (common pattern), that's fine, but it isn't stated anywhere in this repo — document it in OPS-RUNBOOK so "how does code reach production" isn't tribal knowledge, and confirm the CI gates above (build-test, typecheck, lint, e2e, gitleaks) are actually required-checks blocking the deploy trigger rather than running in parallel/independently of it.

## (c) Recommended but not blocking

- [ ] `govulncheck` is intentionally non-blocking for stdlib-only advisories (api-ci.yml:109-112) — reasonable given upstream Go patch-release timing, but confirm someone actually reviews the annotations each run rather than this becoming silent noise.
- [ ] Add a `HEALTHCHECK` instruction directly in `apps/api/Dockerfile` using a tiny compiled Go probe (distroless-compatible) so the image is self-describing regardless of orchestrator, instead of depending solely on `docker-compose.yml`.
- [ ] No `.dockerignore` found for `apps/api` — confirm the Docker build context doesn't pick up `.git`, `apps/api/.env` (which exists on disk per repo listing), or other local-only files during `COPY . .` (Dockerfile line 10).
- [ ] `apps/osrm/start.sh` re-downloads and reprocesses the full Nigeria OSM extract (`osrm-extract` → `osrm-partition` → `osrm-customize`) on any container without a warm `/data` volume — document expected cold-start time in OPS-RUNBOOK so a redeploy/restart isn't mistaken for an outage, and confirm the "persistent volume at /data" mentioned in the `docker-compose.yml` comment (line ~40) is actually provisioned in Railway.
- [ ] Dev-only hardcoded secrets in `docker-compose.yml`, while clearly labeled and low-risk, are still real-looking hex strings in git history — consider moving them to a gitignored `.env.dev` with a committed `.env.dev.example` to reduce gitleaks false-positive churn for new contributors.
- [ ] Section H's rollback guidance says migrations "must be additive/backward-compatible by convention" — this is process, not enforced by tooling. Consider a lightweight CI check (e.g. a migration-linter) if the team wants this convention enforced rather than trusted.
